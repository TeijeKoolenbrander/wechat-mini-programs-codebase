# 点将台: decisions log

Owner: product-ux. Companion to `docs/dianjiangtai/spec.md` (§0 holds the full founder decisions D1-D16 and CTO changes C1-C5) and `docs/dianjiangtai/direction.md`.

This log covers decisions from the v1 re-scope (2026-10-15) onward. Older decisions stay in spec §0 and are not repeated here. IDs:
- **D-n**: founder decision. The CTO relays these; this log never creates one.
- **CTO-Dn**: CTO ruling.
- **PO-n**: product-owner call (product-ux) made within the CTO's rulings. The CTO can reverse any PO call. Founder-level matters (money, credentials, release) are not decided here.

| Date | ID | Decision | Reason | Alternatives considered |
|---|---|---|---|---|
| 2026-10-15 | **D16** | **Merge Phase 0, 1 and 2 into one complete v1 release.** The full game is built in one go. There is no group test, no go/kill gate before the full build and no interim founder approvals. Phase 0 is done. The Phase 1 build is finished and QA-verified (branch history), so v1 = everything already built plus the v1 scope below, then release. The plan is v1 complete build → QA → release pack → Founder Handoff → founder device pass → submission. | Founder decision, relayed by the CTO. | The phased plan (Phase 1 prototype in 15-20 groups for ≥ 7 days, go/kill, then Phase 2). Superseded. |
| 2026-10-15 | **CTO-D1** | **Portraits in v1 are designed seal/monogram portraits, not AI art.** Ink-seal style, in the faction colour, showing the general's name characters, with a frame per tier. Generated in code at runtime, so v1 ships no image assets and needs no CDN. **Supersedes D10's timing:** AI-generated portraits become a post-launch content update. D10's rules (style guide, provenance log, human review, AIGC labels, human-edit trail, off-git hosting) still apply when that update happens. The ICP-filed CDN domain (D9 step 5) is no longer a v1 requirement. | There is no image-generation pipeline. Code-drawn seals carry no likeness, style-imitation or AIGC-labelling risk, add almost nothing to the package, and work offline. | (a) AI portraits in v1: no pipeline, so it blocks release. (b) Commissioned human art: costs money and time, a founder matter, so not v1. (c) Plain one-character monograms as in Phase 1: works, but looks thin at 120 generals. Tier frames and full-name seals make the set feel finished. |
| 2026-10-15 | **CTO-D2** | **v1 scope IN:** 120 generals (晋 faction, 归晋 era, multi-appearance generals, more bonds); seal portraits (CTO-D1); 识人模式; streaks; daily history archive; save card to album; opt-in subscribe message "好友接下了你的战书" (degrades to hidden without a template ID); anti-cheat hardening (progressive per-round daily tokens, `mismatch` anomaly flags); large-text and high-contrast modes; banner ads on board screens behind config (default off); config-driven interstitial tuning; re-tuning so the D15 targets hold. **OUT (post-launch backlog):** 擂台赛, updatable cards, the 视频号 reveal clip, expansion themes (水浒/西游/关公战秦琼/盲排), and the banner A/B experiment. | CTO ruling. 擂台赛 needs gift packs (conflicts with no prizes) and client-reported scores (conflicts with C3). Updatable cards are fixed-template only, so low value. The 视频号 API is unverified. Expansions are outside 三国 only (D13). An A/B test needs live traffic first. | Keep Phase 2 as optional items. Rejected by D16. |
| 2026-10-15 | **CTO-D3** (briefed as "CTO-D2"; that number was already taken by the v1 scope ruling) | **v1 gets audio.** A quiet looping 古琴/琵琶 track (68.6 s) plays low on the home and draft screens and fades out during the battle reveal. Effects: `flip` (wood on lacquer), `drum` (twelve 战鼓 hits, one per battle, ends with the reveal), `bell` (one 编钟 strike for 12-0) and a soft UI `tap`. Settings has two persisted toggles, 音乐 and 音效 (the home 声音 link switches both). Muting is immediate and the game is fully playable muted (AC 49, direction §7). All audio is generated by code in `apps/dianjiangtai/game/tools/audio/` (original melody on the 五声 scale, Karplus-Strong strings, synthesised drum and bell), so there is no licensing exposure. It ships as mp3 in the `audio` subpackage, loaded after launch; missing audio fails silently. | The founder's direction wants a calm, ritual feel, and sound is a large part of the reveal. Procedural generation avoids any unlicensed audio. A subpackage keeps the main package small. | Ship silent (rejected by CTO). Licensed or stock tracks: licence and provenance risk. A single mute switch: players want effects without music and the reverse. |
| 2026-10-15 | **PO-1** | **识人模式 is a weekly special daily: every Sunday (Beijing date), the 今日军令 is a 识人 daily.** Stats, tier, primaryRole, statNote, S_r and fit chips are hidden until the verdict; the sim is identical. No free-play toggle in v1. | A weekly special keeps every player on the same rules on the same day, so boards, challenges and arguments stay fair (pillar 3). It gives the week a rhythm without adding a mode button. Sunday has the most leisure time for our 24-40 / 40+ audience. The sim is unchanged, so tuning, gates, seed bank and server validation need no new work. | (a) Player toggle on the daily: two players on the same board would see different information, which breaks comparability. (b) Free-play toggle: cheap, but it adds a settings surface and doesn't serve the shared argument. Moved to the backlog. (c) 识人 every day: removes the 五德 stat arguments, which are a core hook. |
| 2026-10-15 | **PO-2** | **Multi-appearance data model.** One record per person (one `id`, one stat line), with `appearances: [{faction, eras[], note?}]`. A person can appear in several faction-era cells. **Drafting rule:** a person can be drafted at most once per run, whichever cell they came from. Once drafted, they are excluded (shown dimmed "已点将") in every other cell. **Cohesion** counts the faction of the cell the general was drafted from. Bonds count by person, in any appearance. Stats never differ by appearance. | Keeps one stat line per person (no "two 赵云s" debates, no doubled content review). It needs no change to the action format (`pick` already carries `generalId` and the server knows the round's cell), and it is backward compatible: for single-appearance content, behaviour equals Phase 1. | Separate records per appearance (for example `g_zhaoyun_qun`): doubles stats to review, allows drafting the same person twice, and breaks bonds. Rejected. |
| 2026-10-15 | **PO-3** | **Appearance rule for content.** An appearance needs notable recorded service of about a year or more in that camp. A lord who fought under another lord's banner while leading his own following (刘备 under 公孙瓒/曹操/袁绍/刘表; 孙坚/孙策 under 袁术) keeps his own camp. Short stints go in `statNote` only (for example 关羽 under 曹操 in 200). **晋** = the 司马氏 court from 高平陵 (249) on, plus generals who later served the 晋 state. So 邓艾 and 钟会 (d. 264) are 魏 only, and 司马懿 is 魏 and 晋. The Phase 1 simplifications are corrected now that multi-appearance exists: 张郃 HJ moves 魏 → 群 (under 韩馥); 马超 QX moves 蜀 → 群; 赵云, 张辽 and 黄忠 gain 群 appearances. | Gives reviewers a rule they can check, and the corrections remove the "simplification" footnotes Phase 1 needed. | Keep the Phase 1 placements. Rejected: they were only workarounds for single-faction content. |
| 2026-10-15 | **PO-4** | **v1 roster: 120 generals** (primary faction: 蜀 26, 魏 26, 吴 25, 群 25, 晋 18). 26 generals have appearances in more than one faction. All 21 used faction-era cells have ≥ 4 generals (273 general-cell entries). The 晋 camp exists only in 归晋, so 晋 × 黄巾/群雄/赤壁/三分 are unused cells. The 32 Phase 1 generals keep their exact stats. 16 bonds. Leaders of ethnic-minority uprisings other than 孟获 (for example 轲比能, 秃发树机能) are left out. | Hits the CTO's 120 and roughly 25-35 per faction (晋 is the exception, because the camp only exists in one era). Faction *membership* counting all appearances: 蜀 28, 魏 34, 吴 28, 群 38, 晋 22. The exclusion lowers content-review risk around ethnic-conflict portrayals at no cost to the core loop. | 160 generals: more review load, and thin historical records for the extra names. A larger 晋 roster: it would need obscure names our audience doesn't know. |
| 2026-10-15 | **PO-5** | **Pool cap: a pool shows at most `poolCap` = 8 generals.** They are the first 8 undrafted generals in a deterministic per-round order of the cell (`sub(seed, "pool:"+round+":"+faction+":"+era)`). A cell with ≤ 8 generals shows its whole pool, exactly as in Phase 1. | v1 cells hold up to 27 generals. A 27-row list breaks "one main decision per screen" for older players. The exhaustive 复盘 search grows with pool size^5 (27^5 ≈ 14M sets), while ≤ 8 keeps the Phase 1 worst case (32,768 sets) and the < 300 ms target. It's deterministic, so the daily stays identical for everyone, and it adds variety (each 群雄 round shows a different eight). | (a) Show the whole cell: unreadable and makes 复盘 too slow. (b) Make cells smaller by cutting roster: conflicts with 120. (c) Server-only 复盘 for big cells: still unreadable on screen. |
| 2026-10-15 | **PO-6** | **Streaks:** current streak = consecutive *published* daily dates with a ranked result. Dates with no published seed (`DAILY_UNAVAILABLE`) are skipped and don't break a streak. A `LATE_SUBMIT` friendly does not count. The streak is shown on home, the result and both boards (friends' streaks come from server values). **No rewards of any kind** for streaks, and no streak freeze or repair. | Pillar 4 and direction §9 (no daily-login rewards). Skipping unpublished days stops our own outage from punishing players. | Streak rewards (re-spins, cosmetics): reward-for-login pressure. Rejected. Streak freeze: needs a currency or ads. Rejected. |
| 2026-10-15 | **PO-7** | **Daily history archive:** the last 30 issues. Each shows the player's own result and lineup (or 未出征), the day's record distribution, and that day's best lineup for the primary tokens. The best lineup appears only after the day's submit window closes (D+1 00:30 BJT, same rule as C5). Replaying a past daily as a friendly is **not** in v1 (backlog). | Gives the argument an "answer key" once it can no longer spoil anything. Uses data we already store. | Replay past dailies: more runs per session, but adds a mode and its states. Backlog. Longer archive: little value. Retention is 180 days anyway. |
| 2026-10-15 | **PO-8** | **Progressive daily token delivery:** `getDaily` returns status only. `startRun` (at the first 翻令) returns round 1. A new `getRound` returns round n+1 only after the server has stored the actions through round n's pick. That prefix is then frozen, and `submitRun` must extend it exactly. Re-spin alternatives and pool-empty fallbacks for a round are delivered with that round. The next 翻令 of a daily needs network ("令牌传递中断" plus 重试). The same applies to challenge runs that count as today's daily. Free play is unchanged. | CTO ruling (anti-cheat). Stops planning all five rounds from the full sheet and stops scripted pre-computation. The 1.2 s flip animation hides the round trip. | Signed full sheet with client-side unlock: the client still holds all rounds. Rejected. |
| 2026-10-15 | **PO-9** | **Anomaly flags are observe-only in v1.** `submitRun` and `getRound` write `anomalies` (`mismatch`, `prefix`, `fast`, `invalid_ranked`). A daily aggregate (`cleanup` at 04:00) alerts if the mismatch rate is > 0.5% of runs (a sign of client/server drift). An openid with ≥ 5 flags in 7 days is marked `suspect` for manual review. **No automatic penalties**, and flags never change a result or rank. | Records and ranks are already server-computed (C3), so flags are mostly a bug detector. Automatic bans on a no-prize board add appeal and support load for little gain. | Auto-exclude suspects from boards: risks false positives on honest players with buggy clients. Rejected for v1. |
| 2026-10-15 | **PO-10** | **Subscribe message "好友接下了你的战书":** offered only to the sharer of a challenge, on their tap, after the challenge is created (result screen) or on the own-challenge screen. One one-time grant per challenge, and one message on the first answer. The template ID comes from the remote `app_config` (founder's MP console, Founder Handoff). If it's missing, the button is hidden and nothing errors. No reward. | Opt-in only, tied to the user's own action. Works with no client release once the founder adds the template. | Ask at first launch, or bundle with share: forced or nagging. Rejected. Long-term subscription: not available to games for this use. |
| 2026-10-15 | **PO-11** | **Remote feature config `app_config`** (one cloud DB document, read via `getDaily.features`): subscribe template ID and field map, banner on/off and unit ID, interstitial caps. Missing or unreadable config means everything optional is off. | The founder can switch on the subscribe message and banners (after 流量主) without a code release. | Hard-coded config: needs a release per change. |
| 2026-10-15 | **PO-12** | **Accessibility v1 = large-text mode + high-contrast mode**, both in 设置, saved on the device, combinable. Large text: body ≥ 20 pt, record ≥ 48 pt, buttons ≥ 56 pt tall. High contrast: text ≥ 7:1, non-text ≥ 3:1. Screen-reader labels are backlog: a mini game draws on one canvas with no accessibility tree. | Our audience skews 40+. Both modes are pure rendering changes. | Follow the system font size automatically: the API's coverage is unclear. In v1 it only pre-selects large text on first launch if available (checked in the device pass). |
| 2026-10-15 | **PO-13** | **Seal portrait design** (implements CTO-D1): the full name in a seal layout (2 characters side by side right to left, 3 characters as 1 + 2 columns), in the open-licence display face (宋/楷), not seal script. 1-character `monogram` below 48 pt. Faction colour of the appearance (in pools) or the primary faction (detail sheet). Frames: 甲 double border with corner marks, 乙 single border, 丙 thin weathered border. The tier character is always shown in text, never by frame alone. | 篆书 is hard to read for our audience and few seal-script fonts are open-licence. Full names avoid monogram clashes (渊: 夏侯渊/公孙渊). | Seal script: unreadable at phone sizes. 1-character monograms everywhere: clashes at 120 generals. |
| 2026-10-15 | **PO-14** | **Banner** only on the group and friend boards, in their `ready` and `empty` states (not on the privacy, authorization or error explainers, which have their own buttons). Default **off** until 流量主 exists. | Avoids mis-taps near [去设置开启]/[同意并查看]. Matches the CTO's "board screens only". | Banner in all board states: mis-tap risk next to authorization buttons. |
| 2026-10-15 | **PO-15** | **The go/kill thresholds become post-launch KPIs.** Same definitions (spec §15), with no gate. | D16 removes the gate. The numbers remain the best health signal we have. | Drop them: loses our only benchmarks. |
| 2026-10-15 | **PO-16** | **The real-device spike becomes part of the founder's device pass before submission.** Exit criteria E1-E7 are unchanged, and E8-E12 are added for the v1 APIs. Every criterion already has a specified fallback, so a failure is a dev fix plus re-verification, not a product decision. | D16 (no interim gates) and CTO ruling. | A separate dev spike before the build: no longer possible, since the build exists. |
